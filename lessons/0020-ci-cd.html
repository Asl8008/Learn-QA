20-dars · taxminan 40 daqiqa

Faqat sizning kompyuteringizda ishlaydigan test — himoya emas

19-darsda test yozdik. Lekin uni siz eslab, qo'lda yurgizishingiz kerak. CI shu muammoni yechadi: test har bir o'zgarishda o'zi ishga tushadi.

Muammo

Tanish holat

Testlar yozildi. Birinchi hafta ularni har kuni yurgizasiz. Ikkinchi haftada band bo'lasiz. Uchinchi haftada esdan chiqadi. Bir oydan keyin ularni yurgizsangiz — yarmi yiqiladi va nima uchunligini hech kim bilmaydi.

Yechim: testni odam eslashiga bog'lamaslik. Har safar kod o'zgarganda tizim testlarni o'zi yurgizsin va natijani hammaga ko'rsatsin. Bu — CI (Continuous Integration).

Asosiy tushunchalar

Eng ko'p ishlatiladigan tizim — GitHub Actions. Rasmiy ta'riflar:

TushunchaTa'rif
Workflow Bir yoki bir nechta ishni bajaradigan sozlanadigan avtomatik jarayon
Event Repozitoriydagi muayyan faoliyat — workflow'ni ishga tushiradi
Job Bitta runner'da bajariladigan qadamlar to'plami
Step Bajariladigan buyruq yoki tayyor action
Action Oldindan tayyorlangan, qayta ishlatiladigan qism
Runner Workflow'larni ishga tushiradigan server

Manba: GitHub Docs — Understanding GitHub Actions.

Haqiqiy workflow fayli

Loyihada .github/workflows/playwright.yml fayl yaratiladi. Playwright rasmiy hujjatidagi variant:

name: Playwright Tests
on:
  push:
    branches: [ main, master ]
  pull_request:
    branches: [ main, master ]
jobs:
  test:
    timeout-minutes: 60
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v6
    - uses: actions/setup-node@v6
      with:
        node-version: lts/*
    - name: Install dependencies
      run: npm ci
    - name: Install Playwright Browsers
      run: npx playwright install --with-deps
    - name: Run Playwright tests
      run: npx playwright test
    - uses: actions/upload-artifact@v4
      if: ${{ !cancelled() }}
      with:
        name: playwright-report
        path: playwright-report/
        retention-days: 30

Qator-qator o'qiymiz

QismNima deydi
on: push / pull_request Qachon ishga tushsin: kod yuborilganda va pull request ochilganda
runs-on: ubuntu-latest Qayerda: GitHub beradigan toza Linux server
timeout-minutes: 60 Osilib qolsa, bir soatdan keyin to'xtatiladi
actions/checkout Kodni serverga ko'chirib oladi
actions/setup-node Node.js ni o'rnatadi
npm ci Bog'liqliklarni aniq qulflangan versiyalarda o'rnatadi
npx playwright install --with-deps Brauzer va tizim kutubxonalarini o'rnatadi
npx playwright test Testlarni yurgizadi
upload-artifact Hisobotni saqlaydi — 30 kun yuklab olish mumkin
if: !cancelled() Testlar yiqilganda ham hisobot saqlanadi

Oxirgi ikki qator eng muhimi

Test yiqilganda «nima uchun yiqildi?» degan savol paydo bo'ladi. Hisobot saqlanmasa, javob yo'q — testni qayta yurgizib, ko'rishga urinasiz va u endi o'tib ketadi. upload-artifact esa skrinshot, video va trace ni saqlaydi.

Ya'ni bu — 1-darsdagi dalil tamoyilining CI ko'rinishi.

Qaysi testlar qachon yuradi

Hamma testni har bir o'zgarishda yurgizib bo'lmaydi — sekin bo'ladi. 14-darsdagi piramida shu yerda amaliy qarorga aylanadi:

QachonNima yuradiMaqsad
Har bir commit Unit + API testlar, smoke UI (5–10 daqiqa) Dasturchi darhol javob olsin
Pull request Yuqoridagilar + asosiy UI oqimlari Buzuq kod asosiy tarmoqqa tushmasin
Kechasi To'liq to'plam, bir necha brauzer, mobil o'lchamlar Sekin testlar hech kimni kutdirmasin
Reliz oldidan To'liq regression + qo'lda exploratory Chiqish mezonlarini yopish (9-dars)

Beshinchi daqiqa qoidasi

Har bir commit'da yuradigan to'plam 10 daqiqadan uzun bo'lsa, dasturchilar uni kutmay qo'yadi — natijani ko'rmasdan keyingi ishga o'tishadi va CI o'z ma'nosini yo'qotadi. Tez to'plamni qisqa ushlab turish — testerning doimiy vazifasi.

Qizil build — favqulodda holat

Bu darsdagi eng muhim tashkiliy qoida:

✗ O'lik CI

«Ha, u qizil turibdi, e'tibor bermang, o'sha eski test».

Bu holatda CI hech narsani himoya qilmaydi — u shunchaki shovqin.

✓ Tirik CI

Qizil bo'lsa — hamma to'xtaydi va tuzatadi. Yashil holat normal, qizil holat hodisa.

Bu 14-darsdagi flaky testlar mavzusining davomi: beqaror testlar qizilni odatiy holga aylantiradi va butun tizimni o'ldiradi. Shuning uchun beqaror test darhol tuzatiladi yoki o'chiriladi.

Yiqilgan build'ni o'qish

  1. Loglarni oching — qaysi qadamda to'xtadi? O'rnatishda yoki testda?
  2. Xato xabarini o'qing — Playwright nimani kutgani va nimani topganini aytadi.
  3. Artifact'ni yuklab oling — hisobot, skrinshot, video va trace shu yerda.
  4. Trace'ni oching (npx playwright show-report) — har bir qadamni ko'rish mumkin.
  5. Savolga javob bering: bu haqiqiy bugmi, test xatosimi yoki muhit muammosimi? Uchtasi uch xil harakat talab qiladi.

Ikkinchisi 16-darsdagi mavzuga tegishli: repozitoriyga tushgan parolni o'chirib tashlash yetmaydi — u tarixda qoladi. Shuning uchun uni umuman yozmaslik kerak.

Tekshirib ko'ramiz

1. Workflow faylidagi if: !cancelled() qatori nima uchun kerak?

2. Har bir commit'da yuradigan to'plam 40 daqiqa ishlaydi. Nima bo'ladi?

3. Jamoada «u test doim qizil, e'tibor bermang» degan gap yuradi. Bu nimani anglatadi?

Eslab ko'ring — 19-darsdan: lokatorga bir nechta element mos kelsa Playwright nima qiladi va yechim qanday?

Playwright xato beradi — tasodifiy birini tanlamaydi, ya'ni noaniqlik yashirin qolmaydi. Yechim: doirani toraytirish — avval konteynerni topib (.filter({ hasText: … })), so'ng uning ichidagi elementni tanlash.

Amaliyot: birinchi CI quvuringiz

  1. 19-darsdagi loyihani GitHub'ga joylang. Yangi repozitoriy oching (bepul) va kodni yuboring. node_modules papkasini .gitignore ga qo'shishni unutmang.
  2. Workflow faylini qo'shing: .github/workflows/playwright.yml — yuqoridagi matnni ko'chiring.
  3. Yuboring va kuzating. GitHub'da «Actions» bo'limini oching: qadamlar birin-ketin bajarilishini ko'rasiz.
  4. Yashil natijani ko'ring, so'ng hisobot artifact'ini yuklab olib oching.
  5. Endi ataylab sindiring. Testdagi kutilgan matnni o'zgartiring (masalan 'Products' → 'Mahsulotlar'), yuboring va qizil natijani kuzating.
  6. Yiqilgan build'ni tahlil qiling: loglarni o'qing, artifact'ni yuklab oling, skrinshotni toping. Xato xabari sababni tushuntiryaptimi?
  7. Tuzating va yashil holatga qayting.
  8. Menga yuboring: repozitoriy havolasi va oxirgi band haqida bir xatboshi — qizil build'dan sababni topish qanchalik oson bo'ldi?

Bu portfolio uchun nimani beradi

Repozitoriyingizda ishlaydigan CI bo'lsa, u har bir tashrif buyuruvchiga bitta narsani aytadi: siz test yozgansiz va uni jarayonga ulagansiz. 15-darsdagi portfolio ro'yxatiga qo'shiladigan eng kuchli elementlardan biri — chunki ko'p junior nomzodda bu yo'q.
