Tugmasiz test: API va Postman

6-darsda Network panelida so'rovlarni kuzatdingiz. Endi ularni o'zingiz yuborasiz — interfeys hali yozilmagan bo'lsa ham.

Interfeys — eng ustki qatlam

Siz tugmani bosganingizda quyidagilar sodir bo'ladi:

API (Application Programming Interface) — interfeys bilan server orasidagi kelishuv. Uni to'g'ridan-to'g'ri sinashning uch afzalligi bor:

  • Ertaroq. API odatda interfeysdan oldin tayyor bo'ladi — ya'ni siz kutmasdan test boshlaysiz.
  • Aniqroq. «Xato API dami yoki interfeysdami?» degan savolga javob berasiz.
  • Tezroq. Interfeysda 20 ta variantni qo'lda kiritish yarim soat; API orqali — bir necha daqiqa.

Bu qaysi daraja?

10-darsdagi tasnif bo'yicha API testing — asosan integration darajasi: qismlar orasidagi aloqani tekshirasiz. Shuning uchun unit testlar ko'rmaydigan xatolarning katta qismi aynan shu yerda topiladi.

Idempotentlik — testerning tayyor test g'oyasi

Idempotent degani: so'rovni bir marta yuborsangiz ham, besh marta yuborsangiz ham natija bir xil bo'ladi.

Demak sizda darhol ikkita test bor:

  • DELETE ni ikki marta yuboring. Ikkinchisi xato bermasligi va bazani buzmasligi kerak.
  • POST ni ikki marta yuboring. U idempotent emas — demak ikkita yozuv paydo bo'lishi mumkin. Bu shu holatda to'g'rimi? Ikki xil buyurtma yaratilishi kerakmi yoki dublikat bloklanishi kerakmi? Bu — beriladigan savol.

Foydalanuvchi «To'lash» tugmasini asabiylikdan ikki marta bosganda pul ikki marta yechilishi — aynan shu joydan chiqadigan real xato.

JSON — bir daqiqada

API lar ma'lumotni deyarli har doim JSON shaklida uzatadi:

{
  "id": 42,
  "email": "test@mail.uz",
  "is_active": true,
  "phone": null,
  "orders": [101, 102]
}
  • Matn qiymatlari qo'shtirnoqda, sonlar tirnoqsiz.
  • true / false — mantiqiy qiymat.
  • null — qiymat yo'q. 11-darsdagi NULL ning o'zi.
  • […] — ro'yxat, {…} — obyekt.

Bilishingiz kerak bo'lgan narsa shu. Testerning ishi — javobdagi qiymatlarni kutilgan qiymat bilan solishtirish.

Faqat status kodiga qaramang

200 OK — hammasi joyida degani emas. Body ichida {"error": "user not found"} turishi mumkin. Bu o'zi ham bug: xato holati 200 bilan qaytarilmasligi kerak. Har doim status + body ni birga tekshiring.

Tekshirib ko'ramiz

1. Qaysi metod idempotent emas — ya'ni ikki marta yuborilsa ikkita yozuv paydo bo'lishi mumkin?

2. Majburiy email maydonisiz POST yubordingiz. Server 200 OK qaytardi va body da {"error": "email required"} bor. Bu qanday baholanadi?

3. Nima uchun API ni interfeysdan oldin test qilish mumkin?

Eslab ko'ring — 11-darsdan: nima uchun WHERE phone = NULL ishlamaydi va to'g'ri yozuv qanday?

NULL «noma'lum» degani, noma'lum narsa esa hech narsaga — hatto o'ziga ham — teng emas. Shuning uchun = NULL har doim bo'sh natija qaytaradi. To'g'ri yozuv: WHERE phone IS NULL.

Amaliyot: birinchi API sessiyangiz

Postman ni o'rnating. Mashq uchun jsonplaceholder.typicode.com — bepul, ro'yxatdan o'tish talab qilmaydigan test API.

A qism — tanishuv

  1. GET https://jsonplaceholder.typicode.com/posts/1 yuboring. Status, javob vaqti va body ni ko'ring.
  2. Endi /posts/9999 ni so'rang. Status nima? Body nima?
  3. POST https://jsonplaceholder.typicode.com/posts yuboring. Body → raw → JSON: 
    { "title": "test", "body": "matn", "userId": 1 }
    Status nima? Javobda id paydo bo'ldimi?
  4. Endi yaratilgan id ni GET bilan so'rang. Nima bo'ladi? Bu test serveri ma'lumotni haqiqatan saqlamaydi — u shunday mo'ljallangan. Lekin diqqat qiling: server «yaratdim» dedi, aslida esa yo'q. Real mahsulotda bu jiddiy bug bo'lardi.

B qism — o'z testlaringizni loyihalang

Tasavvur qiling, ro'yxatdan o'tish API si test qilinyapti:

POST /api/register
{ "email": "...", "password": "...", "age": ... }

Talablar: email majburiy va to'g'ri formatda; parol 8–32 belgi; yosh 18–100.

  1. Test holatlarini yozing. 2-darsdagi ekvivalentlik va chegara texnikasidan foydalaning. Kamida 12 ta holat chiqishi kerak.
  2. Har biriga kutilgan status kodini yozing.
  3. Kamida uchtasi faqat API darajasida sinaladigan holat bo'lsin — interfeys orqali umuman yubora olmaydigan narsalar (masalan age maydoniga matn, yoki maydonni butunlay olib tashlash).
  4. Menga yuboring: jadval ko'rinishida — holat, yuborilgan ma'lumot, kutilgan status, kutilgan xato matni.

3-band nima uchun muhim

Interfeys sizni himoya qiladi: yosh maydoniga faqat son kiritishga ruxsat beradi, bo'sh formani yubortirmaydi. Lekin haqiqiy hujumchi interfeysdan foydalanmaydi — u so'rovni to'g'ridan-to'g'ri yuboradi. Server o'zi ham tekshirishi shart. Aynan shu joyda API testerlari eng qimmatli xatolarni topadi.
